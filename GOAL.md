## 0. ГЛАВНОЕ ПРАВИЛО: ВСЁ ДОЛЖНО БЫТЬ ВАНИЛЬНО

**Поведение ezzmc обязано совпадать с ванильным Minecraft Java Edition до мелочей** — для каждой поддерживаемой версии.

Это значит:
- Физика, движение, коллизии, тики, урон, голод, чат, инвентарь, мир, свет, рендер блоков/моделей/освещения — **как в ванили**, включая «баги-фичи» (если они ванильные и их ждут серверы/игроки).
- Формат и порядок пакетов, тайминги, keep-alive, поведение при ошибках и дисконнектах — как у ванильного клиента: сервер не должен отличать нас от оригинала (анти-читы тоже).
- Брендинг `vanilla` в handshake/brand-пакете, ванильные настройки по умолчанию, ванильный UI-поведенческий контракт.
- **Никаких «улучшений» геймплея и отсебятины.** Оптимизация (Столп 1) допустима только если результат **бит-в-бит/кадр-в-кадр эквивалентен ваниле** (тот же мир, тот же меш, те же пакеты, та же физика). Если оптимизация меняет наблюдаемое поведение — она **запрещена**.
- Любое расхождение с ванилью — **баг**, записывается в `STATUS.md → Баги` с пометкой `[vanilla-diff]`, severity не ниже `high`.
- Спорный вопрос «как в ванили?» решается **только по оригинальному исходнику/данным** (§2А), а не по памяти, догадкам или «так логичнее».

Приоритет правил: **Ванильность > Корректность > Производительность > Удобство кода.**

## 0Б. РЕЖИМ ПРОЕКТА: личный, приватный, оффлайн

Решение владельца (действует над всеми остальными разделами, при конфликте прав §0Б):
- Проект **полностью приватный**, для личного некоммерческого использования, **никогда не публикуется**. Репозиторий GitHub — приватный.
- **Аккаунтов нет.** Нет Microsoft/Mojang авторизации, нет токенов, нет менеджера аккаунтов, нет sessionserver. Только **offline-логин**: ник + UUID по ванильной offline-схеме (`UUID.nameUUIDFromBytes("OfflinePlayer:" + name)`).
- **Всё оффлайн и на компьютере владельца.** Целевые серверы — локальные/приватные в `online-mode=false` (и с `enforce-secure-chat=false`). Серверы с `online-mode=true` вне цели — шифрование соединения не требуется (опционально P3).
- **Столп №2 (мульти-версии 1.5.2 → latest) НЕ ослабляется:** клиент обязан заходить на серверы **любой** версии из диапазона, у которых в `server.properties` стоит `online-mode=false`. Отсутствие аккаунтов сужает только способ входа (offline), но не список версий и не глубину поддержки протоколов. Тестовый стенд для каждой версии — ванильный сервер с `online-mode=false`.
- **Подпись чата не нужна:** клиент шлёт unsigned-чат, как ванильный клиент без профиля ключей.
- **Скины:** только локальные (файл) или дефолтные Steve/Alex по UUID. Сетевой загрузки профилей/скинов/плащей нет.
- **Лицензии и публикация нас не касаются:** можно свободно использовать исходник Mojang как эталон и переводить его логику на Rust. Реалии «распространения» (релизы, подписи, автообновление, Realms) — не цель.
- Это расширяет возможности агентов (брать оригинальный код как основу порта), но **не отменяет** §0 (ваниль) и §7А (дисциплина и штрафы).

## 1. Суть проекта

**ezzmc** — полностью самостоятельный клиент Minecraft: Java Edition, написанный на **Rust** с нуля. Не обёртка над официальным клиентом, не лаунчер Java, не зависимость от JVM, не зависимость от дампов из Java-клиента.

Два столпа, ради которых проект существует:

1. **Максимальная оптимизация всего.** Клиент должен быть быстрейшим из возможных: старт, загрузка чанков, меш, рендер, сеть, память, ввод.
2. **Универсальная совместимость по протоколам.** Один клиент заходит на **любой** сервер любой версии **от 1.5.2 до последней (на сегодня 26.3)** и умеет обновляться на новые версии с минимальной ценой.

Целевая («родная») версия — **последняя выпущенная**. Все старые версии поддерживаются через слой трансляции протоколов (см. §4), а не через отдельные копии клиента.

> Номера версий считаем по актуальной схеме Mojang (после 1.21.x идёт схема `26.x`). Перед любой работой, зависящей от точных номеров версий или протоколов, **проверь их по первоисточнику** (wiki.vg / minecraft.wiki / `version.json` из официального манифеста), а не по памяти.

## 2. Не-цели (чего НЕ делаем)

- Не запускаем Java, не вызываем оригинальный клиент, не читаем его память.
- Не публикуем проект (§0Б). Оригинальный исходник/ассеты Mojang по умолчанию держим локально в `reference/` (в `.gitignore`, чтобы не раздувать репозиторий); в наш код логику **переводим на Rust** с эталона, дословный перенос алгоритма допустим.
- Встроенный сервер (одиночный мир) — **планируется позже** (`TASKS.md`, глава 22), сейчас не делаем; до этого играем на внешнем ванильном сервере с `online-mode=false`.
- Не делаем моды/Forge/Fabric-совместимость.
- Не жертвуем производительностью ради «красоты кода» без измерений.

## 2А. Эталонные исходники: читать оригинал и переводить на Rust

Писать с нуля «по памяти» = гарантированные расхождения с ванилью. Поэтому **для любой игровой логики сначала открывается оригинал, потом пишется Rust-порт.**

### Что можно и нужно смотреть
- **Деобфусцированный исходник клиента (и сервера) нужной версии** с официальными маппингами Mojang (Mojmap) — получается локальным декомпилятором из официального `client.jar`/`server.jar` с официальным `client.txt`/`server.txt` маппингом (манифест Mojang). Для каждой версии — своя копия.
- **Официальный Data Generator** (`java -DbundlerMainClass=net.minecraft.data.Main -jar server.jar --reports --server`) — пакеты, регистры, блоки, предметы, команды, теги, биомы, рецепты.
- **Описания протокола** (wiki.vg-архив / minecraft.wiki), открытые реализации (ViaVersion/ViaBackwards, Valence, Pumpkin, minecraft-protocol, prismarine-*, Azalea и т. п.) — как **перекрёстная проверка** и для старых версий. Первичный источник — всё равно оригинальный код.
- **Соседние Rust-клиенты владельца (локально, только чтение)** — вторичный источник, готовые решения для сверки и ускорения:
  - **Pomme** — `~/pomme` (крейты `pomme-protocol`, `pomme-client`, `pomme-block`, `pomme-auth`, `pomme-singleplayer`…): клиент Rust+Vulkan, заходит на ваниль **1.20 → 26.3**. Самый полезный для новых версий (протокол, регистры, рендер, GUI).
  - **Horizon / EzzzingCraft 1.20.1** — `~/horizon-1.20.1` (крейты `horizon-protocol`, `horizon-world`, `horizon-assets`, `horizon-viewer`, `horizon-core`; протокол 763, wgpu; заметки `NOTES.md`, `PORT-1.20.1.md`, `BUGS.md`) и `~/horizon-launcher` (большой workspace `crates/horizon-*`, клиент/рендер/ввод/чат/боты, `docs/`, `ROADMAP.md`). Код владельца — можно заимствовать свободно.
  - **chunker-worldgen** — https://github.com/mochensky/chunker-worldgen (Rust, MIT/Apache-2.0, только 26.3): побитовая генерация мира ванили (биомы, рельеф, пещеры, features, структуры). **Только для главы 22** (TODO-463…468); для M1/сети/чанк-пакетов/мешей бесполезен. Проект молодой (7 коммитов, один автор): «бит-в-бит» не принимать на веру, сверять с `reference/`. Читать/портировать, не подключать как зависимость; пометка `// FROM: chunker-worldgen/<путь>`.
  - Правила: (1) это **не истина о ванили** — в них есть баги и расхождения; спорное решает оригинальный исходник Mojang; (2) только читать и портировать идеи/алгоритмы в наш код, **не менять** их файлы и **не подключать как Cargo-зависимость** (проект самодостаточен); (3) покрытие: Pomme — от 1.20, Horizon — 1.20.1; **всё, что старше 1.20, придётся делать по эталону Mojang и спискам протоколов**; (4) копируя из них, ставь комментарий `// FROM: pomme/<путь>` или `// FROM: horizon/<путь>` + при расхождении с эталоном — `[vanilla-diff]`; (5) сначала смотри `CODEMAP`/`docs/ref`, потом соседние клиенты, потом уже сам эталон только если нужно проверить.
- Реальный трафик: записи сессий ванильного клиента с ванильным сервером нужной версии (replay) — **эталон для тестов**.

### Как работать с эталоном
1. Эталон лежит в **`reference/<версия>/`** (или за пределами репозитория), путь в `.gitignore`. По умолчанию не коммитится (размер и порядок, не юридический запрет — см. §0Б). Получение — скриптом `xtask fetch-reference <версия>` (скачать jar → маппинги → декомпиляция), чтобы каждый агент мог воспроизвести.
2. Порядок: **найди класс/метод в эталоне → пойми алгоритм → перепиши идиоматично на Rust с тем же поведением** (порядок операций, порядок float-вычислений, округления, константы, `int`/`long` переполнения, порядок обхода — всё важно для бит-в-бит совпадения).
3. В каждом портированном месте оставляй ссылку-комментарий: `// VANILLA: net.minecraft.world.entity.Entity#move (1.21.x)` — **имя класса и метода, без вставки кода**. Так любой агент найдёт эталон и сверит.
4. Java-семантику переносить **точно**: `float` ≠ `double`, `Math.sin` в Java = таблица `Mth.sin`, переполнение `int`, `>>` vs `>>>`, `Random` = LCG Java, порядок вычислений float. Тесты сверяют результаты с эталоном (golden-тесты: значения, снятые с настоящей ванили, лежат в `tests-integration/golden/` как **данные**, не код).
5. Для **старых версий** (1.5.2 → 1.12) берём исходник **той** версии (MCP-маппинги), а не «примерно как в новой».
6. Выжимки из эталона, которые пригодятся другим агентам (карта классов, таблицы констант, схемы пакетов), пишутся своими словами в **`docs/ref/*.md`** — чтобы **не перечитывать огромные исходники в каждом чате** (экономия токенов, §7А). Это наши заметки, а не копия кода.

### Лицензии и приватность
См. §0Б: проект личный и приватный, лицензионные ограничения на публикацию нас не касаются. Ассеты по-прежнему читаются из установленной локально игры (не дублируем гигабайты в git), а исходники Mojang лежат в `reference/` как справочник.

## 3. Столп №1 — Максимальная оптимизация

Оптимизация — не стадия «потом», а **критерий приёмки каждой фичи**.

### 3.1 Принципы
- **Измеряй, потом оптимизируй.** Любое «ускорение» без бенчмарка/профайла = недействительно. Результаты заносятся в `STATUS.md → Бенчмарки`.
- **Data-oriented design:** плоские массивы, SoA, ECS где оправдано, минимум аллокаций в горячих путях, zero-copy парсинг пакетов.
- **Ноль аллокаций в кадре** в steady state (арены, пулы, переиспользуемые буферы).
- **Многопоточность по умолчанию:** разбор сети, декомпрессия, генерация мешей, загрузка ресурсов — вне главного потока. Рендер-поток не блокируется ничем.
- **GPU-driven рендер:** wgpu/Vulkan, indirect draw, culling на GPU/по секциям, greedy meshing / компактные вершины (упакованные в u32/u64), texture arrays/atlas, мешинг чанков асинхронно с приоритетом по расстоянию и направлению взгляда.
- **Сеть:** потоковый парсер, libdeflate/zlib-ng для сжатия, батчинг, предвыделенные буферы, быстрые таблицы id→тип.
- **Память:** компактные палитры секций (как в протоколе), bit-packed хранение, mmap для ресурсов, ленивая распаковка.
- **Холодный старт** — цель в миллисекундах-десятках миллисекунд до окна; ресурсы грузятся лениво/параллельно, кэш пре-обработанных данных на диске.
- **Сборка:** `opt-level=3`, `lto="fat"`, `codegen-units=1`, `panic="abort"` для релиза, PGO/BOLT где даёт выигрыш, `target-cpu` профили, SIMD (std::simd / явные intrinsics с рантайм-детектом).
- **Оптимизация не меняет ваниль (§0):** оптимизированный и эталонный путь сравниваются тестом на идентичный результат (меш, пакеты, физика).
- Стабильность важнее: оптимизация **не имеет права** ломать корректность. Каждая «хитрая» оптимизация покрывается тестом и комментарием `// PERF:` с объяснением почему и на сколько.

## 4. Столп №2 — Мульти-версионные протоколы (1.5.2 → 26.3+)

Нужна **полная таблица протоколов всех версий Minecraft** и возможность подключиться к серверу любой из них.

### 4.1 Архитектурная идея
Не N клиентов и не `if version == …` по всему коду. Вместо этого:

```
   Сервер (версия X)  <──wire X──>  [ Codec версии X ]
                                          │  (декод/энкод пакетов X)
                                          ▼
                                [ Translator X → Canonical ]
                                          │
                                          ▼
                       Каноническая модель (= последняя версия)
                                          │
                                          ▼
                              Ядро клиента (мир, рендер, логика)
```

- **Каноническая модель** = протокол/состояние мира **последней версии**. Ядро клиента знает только её.
- Для каждой версии/эры — **кодек + транслятор** в каноническую модель (и обратно для исходящих пакетов).
- Трансляторы **цепочечные**, где это возможно (X → X+1 → … → latest), как в ViaVersion: добавление новой версии = один новый шаг цепочки, а не переписывание всего. Где цепочка даёт потерю данных или слишком медленна — допускается прямой транслятор «эра → latest» (с пометкой `// PERF:`).
- Данные версий (протокольные id, регистры блоков/предметов/сущностей, форматы чанков, NBT/компоненты) — **описаны данными** (генерируемые таблицы/файлы), не размазаны по коду.
- Выбор версии: автодетект через Server List Ping (handshake/status) + ручное переопределение.

### 4.2 Эпохи протокола (ориентир; номера проверять по первоисточнику)
| Эра | Особенности |
|---|---|
| **Pre-Netty** (1.5.2 – 1.6.4, protocol ≈ 61–78) | Свой бинарный формат, без VarInt-фрейминга, `0xFA` plugin messages, `0xFE` ping, шифрование RC4-подобное по сокету по-своему, чанки Gzip/zlib целиком, ID блоков 8/12 бит |
| **Netty ранний** (1.7.x, protocol 4–5) | VarInt-фрейминг, состояния Handshake/Status/Login/Play, ещё старые чанки и meta |
| **1.8** (protocol 47) | Компрессия пакетов, позиции пакованы в long, новые чанки, массовое использование сервера в PvP — **приоритетная версия** |
| **1.9 – 1.12** (107–340) | Вторая рука, новые пакеты движения, изменения метаданных |
| **1.13 «Flattening»** (393+) | Новые id блоков/предметов, Brigadier-команды, новая палитра |
| **1.14 – 1.15** (477–578) | Новая светосистема, heightmaps, POI |
| **1.16 – 1.17** (735–755) | Dimension codec, NBT-изменения, высоты мира |
| **1.18 – 1.19.x** (757–763) | Высота −64..320, signed chat, chat reports |
| **1.20.2+** (764+) | **Состояние Configuration**, chunk batch, ужесточённый формат |
| **1.20.5 – 1.21.x** (766+) | Data components вместо NBT предметов, новый формат пакетов |
| **26.x** (последняя) | Каноническая версия (целевая) |

> Эта таблица — ориентир. **Истина** лежит в `protocol/versions.*` (см. §6) и обязана содержать: имя версии, protocol number, data version, дату релиза, эру, наличие Configuration-состояния, формат чанка, схему шифрования/компрессии, статус поддержки.

### 4.3 Что значит «поддерживается версия» (Definition of Done для версии)
Версия считается поддерживаемой, только если:
1. Есть запись в таблице версий с корректным protocol number.
2. Работает: ping/status → handshake → login (**только offline-режим**, сервер с `online-mode=false`, §0Б) → Play.
3. Корректно грузятся и рендерятся чанки (включая свет, биомы, блок-сущности там, где это нужно).
4. Работают базовые вещи: движение, чат, инвентарь, блоки (ломать/ставить), сущности/игроки, смена измерения, keep-alive, resource pack, disconnect.
5. Есть **интеграционный тест** против реального сервера этой версии (или записанного трафика/replay), добавленный в CI.
6. Запись об этом внесена в `STATUS.md → Матрица версий`.

Статусы в матрице: `—` не начато · `ping` · `login` · `play-min` · `play-full` · `verified`.

### 4.4 Обновление на новую версию (Minor-update workflow)
Выходит новая версия Minecraft → обновление проекта должно быть **процедурой, а не героизмом**:
1. Скачать официальные данные (`--reports`, манифест) → прогнать генератор данных → получить новые таблицы пакетов/регистров/блоков.
2. Сделать diff с предыдущей канонической версией.
3. Обновить каноническую модель (ядро).
4. Добавить **один** новый транслятор «предыдущая каноническая → новая каноническая» и включить его в цепочку для всех старых версий.
5. Прогнать полный набор тестов матрицы версий — регрессий быть не должно.
6. Обновить `STATUS.md` и этот файл (номер последней версии).

Инструмент (`xtask update-version <ver>`) для шагов 1–2 — обязательный deliverable, см. дорожную карту.

## 5. Архитектурные принципы (общие)

- **Язык:** Rust (stable, edition последняя). `unsafe` — только в горячих путях, с `// SAFETY:` и тестом/миром Miri где возможно.
- **Workspace из крейтов**, строгие границы:
  - `protocol` — кодеки, пакеты, таблицы версий, трансляторы (без зависимостей от рендера).
  - `net` — сокеты, шифрование, компрессия, async-рантайм сети.
  - `world` — чанки, секции, палитры, свет, блоки, сущности (каноническая модель).
  - `mesh` — построение мешей, atlas, culling.
  - `render` — wgpu, пайплайны, шейдеры.
  - `client` — игровая логика, ввод, физика, UI, главный цикл.
  - `assets` — ресурспаки, текстуры, звуки, модели, кэш.
  - `data` / `xtask` — кодогенерация из официальных отчётов, утилиты обновления версий.
  - `tests-integration` — тесты против реальных серверов/реплеев.
- **Кодогенерация вместо ручного ввода** для всего, что зависит от версии (id пакетов, блоков, предметов, сущностей).
- **Детерминизм и тестируемость:** сетевой слой и мир тестируются без окна и GPU.
- **Безопасность сети:** сервер — недоверенный источник. Любой длина/индекс/VarInt проверяется, лимиты на размеры, никаких паник от плохих данных (паника = баг уровня critical).
- **Кроссплатформенность:** Linux — основная, Windows и macOS не ломаем.
- **Зависимости:** осознанно, минимум, без тяжёлых фреймворков ради мелочей. Каждая новая тяжёлая зависимость обсуждается в `STATUS.md → Решения`.

## 7. ПРАВИЛА ДЛЯ АГЕНТОВ (обязательны)

Проект ведут **много агентов из разных чатов, без общей памяти.** Единственная общая память — файлы в репозитории. Поэтому:

### 7.1 Начало работы (всегда)
1. Прочитай `CLAUDE.md` (порядок чтения и решённые вопросы), `GOAL.md` — по разделам при необходимости.
2. В `STATUS.md` читай **Текущий фокус**, **Следующие шаги**, **Блокеры**, свежие строки журнала; остальное — по необходимости.
2а. Открой `CODEMAP.md` — карта, где что лежит (§7.9). Код ищи через неё.
3. Посмотри `git log -n 20` и `git status`.
4. Если задача пользователя противоречит GOAL.md — скажи об этом, не выполняй молча.

### 7.2 Во время работы
- Работай **в рамках целей** GOAL.md. Не добавляй фичи «от себя» вне двух столпов.
- Нашёл баг, который не чинишь сейчас → **сразу** запиши в `STATUS.md → Баги`.
- Придумал/увидел недоделку → **сразу** запиши в `STATUS.md → TODO`.
- Принял архитектурное/технологическое решение → запиши в `STATUS.md → Решения` (что, почему, какие альтернативы отвергнуты).
- Узнал нетривиальный факт о протоколе (баг/особенность версии) → `STATUS.md → Заметки по протоколам`.

### 7.3 Конец работы (всегда, до ответа пользователю)
Перед завершением ответа **обязательно обнови `STATUS.md`**:
- добавь запись в **Журнал изменений** (дата, что сделано, какие файлы/крейты, зачем);
- обнови **Матрицу версий**, если статус какой-то версии изменился;
- обнови **Бенчмарки**, если делал оптимизации (до/после, чем мерил);
- закрой выполненные TODO/баги (перенеси в «Сделано»/пометь `[x]` с датой), добавь новые;
- обнови **Текущий фокус** и **Следующие шаги**, чтобы следующий агент без вопросов продолжил.

> **Правило золотое:** если ты изменил код, а `STATUS.md` не изменил — работа не закончена.
> Исключение: чисто косметическая правка без смысловых изменений (форматирование). Даже тогда — строка в журнале.

### 7.4 Формат записей (чтобы файл не превращался в свалку)
- Даты: `YYYY-MM-DD` (абсолютные, никаких «вчера»).
- Журнал: новые записи **сверху**, одна запись = 1–5 строк.
- Баги: `- [ ] BUG-NNN [severity] краткое описание — как воспроизвести — где (файл:строка) — дата`. Severity: `critical | high | medium | low`.
- TODO: `- [ ] TODO-NNN [P0..P3] описание — зависимости — дата`.
- Номера (BUG-/TODO-/DEC-) сквозные, не переиспользуются.
- Закрытое: `- [x] ... (закрыто YYYY-MM-DD, коммит abc1234)`. Старое закрытое можно архивировать в `STATUS.md → Архив`, но не удалять.
- Не раздувай: коротко, по делу, ссылки на файлы/коммиты вместо простыней кода.

### 7.5 Качество кода (минимум для коммита)
- `cargo fmt`, `cargo clippy -- -D warnings`, `cargo test` проходят.
- Новая оптимизация → бенчмарк (`criterion`/`divan`) и запись в `Бенчмарки`.
- Новая версия протокола/изменение кодека → тест на реальных/записанных пакетах.
- Никаких `unwrap()`/`expect()`/индексации без проверки на пути обработки сетевых данных.
- Репозиторий приватный (§0Б): не делай его публичным и не заливай во внешние сервисы без прямой просьбы владельца.
- Ассеты Mojang читаются из локальной установки игры, в git их не дублируем (размер). Исходники-эталон — в `reference/`.

### 7.6 Коммиты
- Маленькие, атомарные, осмысленные: `protocol/1.8: decode chunk data bulk`.
- `STATUS.md` обновляется в **том же коммите**, что и код (или в соседнем сразу за ним).
- Не переписывай историю общей ветки. Не делай коммиты/пуши, если пользователь этого не просил.

### 7.7 Автономность и честность
- Не оставляй «заглушки, о которых забыл»: каждая заглушка — `// TODO(TODO-NNN)` и запись в STATUS.md.
- Не рапортуй «готово», если не проверено. Пиши честно: что работает, что нет, что не проверено.
- Если упёрся в блокер (нет сервера нужной версии, нет данных) — запиши в `STATUS.md → Блокеры` и иди к следующей задаче, не вставай.
- Не трать ресурсы на то, чего пользователь не просил. Сначала делай прямо, а не плоди сложные схемы.

### 7.7А Ваниль и эталон
- Перед портом игровой логики — открой эталон (§2А). Писать по памяти поведение игры **запрещено**.
- Каждый портированный фрагмент помечен `// VANILLA: класс#метод (версия)`.
- Нашёл расхождение с ванилью — `[vanilla-diff]` в Баги, не «подгоняй» молча.

### 7.9 Карта кода (`CODEMAP.md`)
- **Поиск кода начинай с `CODEMAP.md`**, а не с обхода всего проекта: найди тему/файл в карте и иди сразу туда (экономия токенов, §7А).
- **Создал, переместил, переименовал или удалил файл — или добавил важный тип/функцию — обнови `CODEMAP.md` в том же коммите.** Формат записи — в самом файле.
- Не нашёл нужное в карте и пришлось искать `rg` → после нахождения **добавь запись** в карту.
- Нашёл расхождение карты с кодом → исправь сразу; если нет времени — `[codemap]` в `STATUS.md → Баги`.
- Карта содержит только пути, назначение и связи — не код. Одна запись на файл, ≤ 6 строк.
- Нарушения: не обновил карту после изменения структуры — 2 ШБ; карта врёт и это привело к лишнему поиску — 1 ШБ.

### 7.10 Задачи (`TASKS.md`)
- Бэклог проекта — `TASKS.md`, разбит на главы 0–21 («от запуска окна до убийства дракона»). Задачи берутся **по порядку глав**, сверху вниз, P0 → P1 → P2 → P3.
- Взял задачу — отметь `[~]` с чатом/датой; закончил — `[x]` с датой и коммитом; не смог — верни `[ ]` и запиши `Блокер`.
- Новая задача — в конец подходящей главы с номером из строки «Следующий свободный номер»; сразу обнови эту строку.
- Прыгать между главами или брать задачу вне Фокуса без записи `DEC` — нарушение (3 ШБ, §7А).

### 7.8 Конфликты между агентами
- Параллельные чаты могут править `STATUS.md` одновременно. Перед правкой перечитай актуальную версию файла; правь точечно (добавляй строки), не переписывай разделы целиком.
- При мерж-конфликте в `STATUS.md` — сохрани **обе** стороны, не теряй чужие записи.

## 7А. ЛИМИТЫ, ДИСЦИПЛИНА И ШТРАФЫ

Токены и лимиты — ограниченный ресурс владельца. Агент, который тратит их хаотично, **вредит проекту**, даже если «что-то написал». Цель: **максимум продвижения к GOAL на минимум токенов, строго по задаче.**

### 7А.1 Бюджет задачи
Перед началом выбери класс задачи и **объяви его одной строкой** в начале работы (и в журнале):

| Класс | Пример | Потолок |
|---|---|---|
| **S** | починить баг, добавить одно поле пакета | ≤ 15 вызовов инструментов, ≤ 5 файлов прочитано целиком |
| **M** | кодек одного пакета/семейства, один модуль | ≤ 40 вызовов, ≤ 12 файлов |
| **L** | целая подсистема (чанки, один транслятор версии) | ≤ 100 вызовов; **сначала план ≤ 15 строк**, записанный в STATUS.md |

Потолок превышен → **остановись**, зафиксируй состояние в `STATUS.md`, сообщи пользователю, что осталось, и спроси разрешение продолжить. Не «дорабатывай ещё чуть-чуть».

### 7А.2 Правила экономии
1. **Сначала поиск, потом чтение.** `grep`/`rg`/символьный поиск → читай только нужный диапазон строк. Не читай файл целиком, если нужна функция. Не читай огромные декомпилированные файлы целиком — сначала `docs/ref/`.
2. **Не перечитывай** то, что уже в контексте. Не повторяй вывод тестов/логов в ответе.
3. **Один чат — одна задача.** Не берись за соседнее «заодно». Нашёл соседнее — запиши в TODO.
4. **Один осмысленный запуск вместо десяти.** Не гоняй `cargo build` после каждой строки; чини пачкой, проверяй целенаправленно (`cargo check -p <крейт>`, один тест, а не весь workspace, пока не финал).
5. **Субагенты — только если реально нужны** (параллельная независимая работа). Не плоди их для поиска «на всякий случай»: каждый стартует с нуля и стоит токенов. Прямая работа дешевле.
6. **Правило трёх попыток.** Одна и та же ошибка не поддаётся после 3 разных попыток → стоп: запиши в `Блокеры`/`Баги` что пробовал и что выяснил, переходи к другой задаче или спроси пользователя. Никаких бесконечных циклов «попробуем ещё».
7. **Короткие ответы.** Итог = что сделано, что не сделано, что дальше. Без пересказа диффа и без портянок кода в чате — код в файлах.
8. **Никаких «больших переписываний»** (rewrite, масштабный рефакторинг, смена архитектуры) без записи `DEC-NNN` и согласия пользователя.
9. **Не генерируй мусор:** лишние README, дубли документов, «на будущее» абстракции, мёртвый код, скрипты «для удобства», которые никто не просил.
10. **План ≠ код.** Для L-задач план короткий; не пиши эссе в чат и в STATUS.

### 7А.3 Что считается «хаотичной работой» (нарушением)
- Работа вне двух столпов и вне текущего **Фокуса** из STATUS.md.
- Сделано больше (или другое), чем просили.
- Правка игрового поведения **без** чтения эталона (§2А) / отсебятина против §0.
- Чтение 10+ файлов «для ознакомления» без вопроса, на который ищется ответ.
- Повтор уже сделанного/зафиксированного (игнор `STATUS.md`).
- Бесконечный цикл правок одной и той же ошибки (>3 попыток).
- Заглушки без `TODO(TODO-NNN)`, «готово» без проверки.
- Изменил код, не обновил STATUS.md.
- Неоправданные субагенты, массовые перезаписи файлов, смена зависимостей без `DEC`.
- Нарушение потолка бюджета без остановки.

### 7А.4 Система штрафов
Штрафные баллы **ШБ** записываются в `STATUS.md → Журнал нарушений` (кто/какой чат, дата, пункт, баллы). Агент обязан **сам** записывать свои нарушения, как только заметил; пользователь и ревьюер тоже могут добавлять.

| Нарушение | ШБ |
|---|---|
| Не прочитал GOAL.md/STATUS.md до работы | 2 |
| Работа вне Фокуса/столпов, лишние фичи | 3 |
| Превысил потолок бюджета (§7А.1) и не остановился | 3 |
| Игровая логика «по памяти» без эталона / расхождение с ванилью по отсебятине | **5** |
| Оптимизация изменила наблюдаемое поведение (нарушен §0) | **5** |
| Не обновил STATUS.md после изменений | 2 |
| «Готово» без проверки / заглушка без TODO | 2 |
| Цикл >3 попыток вместо стопа | 2 |
| Лишние субагенты/мусорные файлы/ненужный рефакторинг | 2 |
| Публикация репозитория/кода наружу без прямой просьбы владельца | **10** (немедленный откат) |
| Реализация аккаунтов/Microsoft-авторизации/онлайн-логина вопреки §0Б | 3 |
| Переписал/удалил чужие записи в STATUS.md | 3 |

**Последствия по накопленным ШБ (за текущую сессию/задачу):**
- **1–3 ШБ — предупреждение.** Запись в журнале, исправить немедленно.
- **4–6 ШБ — режим «узкий фокус».** Агент делает **только** исправление своих нарушений и текущей задачи класса S; новые задачи запрещены до подтверждения пользователя.
- **7–9 ШБ — режим «под присмотром».** Перед каждым изменением кода — план из 3–5 строк и ожидание подтверждения пользователя; запись в STATUS.md после каждого шага.
- **10+ ШБ — стоп.** Сессия прекращает работу, оформляет отчёт (что сделано, что сломано, что откатить) и передаёт управление пользователю. Новая сессия начинает с разбора этого отчёта.

Нарушения **не стираются**; закрытые помечаются `[исправлено]`, но остаются как история. Повторное нарушение того же пункта = **двойные баллы**.

### 7А.5 Поощрения (что хорошо)
Фиксируется в журнале как `+1 доверие`: задача закрыта в рамках бюджета; найден и записан `[vanilla-diff]` до того, как он сломал что-то; добавлен golden-тест с реальной ванили; выжимка в `docs/ref/` сэкономила чтение другим. Накопленное доверие снижает порог строгости (по решению пользователя), но **не отменяет** штрафы.

## 8. Дорожная карта (укрупнённо; детали и статус — в STATUS.md)

## 9. Критерии успеха проекта

1. Клиент на Rust заходит и играет на сервере **последней** версии без JVM.
2. Тот же бинарник заходит на **любую** версию 1.5.2 → последняя; матрица версий в `STATUS.md` подтверждает это.
3. Производительность по всем метрикам из §3.2 лучше ванильного клиента с запасом, подтверждена бенчмарками.
4. Выход новой версии Minecraft добавляется по процедуре §4.4 без переписывания ядра.
5. Любой новый агент за 10 минут чтения GOAL.md + STATUS.md понимает, что делать дальше.
