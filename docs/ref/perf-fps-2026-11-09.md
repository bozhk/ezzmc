## 1. Быстрый старт профилирования (работает)

- `cargo f` (alias в `.cargo/config.toml`) = `cargo build --profile fast -p ezzmc-client` → `target/fast/ezzmc-client`.
  Профиль `fast` (Cargo.toml) теперь с `debug="line-tables-only"` и `strip="none"` — для samply.
- **Релизный профиль вырезает символы** (`strip = "symbols"` в `[profile.release]`). Для профиля релиза:
  `CARGO_PROFILE_RELEASE_DEBUG=true CARGO_PROFILE_RELEASE_STRIP=none cargo build --release -p ezzmc-client` (~1.5–2.5 мин, fat LTO).
  Это перезаписывает `target/release/ezzmc-client`, которым пользуется MCP `game_launch`.
- `samply` установлен: `~/.cargo/bin/samply` (в PATH шелла Bash его нет — вызывать по полному пути).
  `echo -1 | sudo tee /proc/sys/kernel/perf_event_paranoid` — уже сделано пользователем, сбрасывается при перезагрузке.
- Запись без браузера: `samply record --save-only --no-open -o <dir>/profile.json <бинарник> --connect 127.0.0.1:25611`
  (имя без `.gz` → файл **не** сжат; с `.gz` — gzip. Скрипты ниже понимают оба).
- Подключение к уже запущенному процессу (после `game_launch` MCP): `samply record -p <PID> --save-only --no-open -o ...`;
  `-d` с `-p` **не работает** — остановить `pkill -INT -x samply` и подождать ~10 с.
- Профиль в samply — **без символов**: в `profile.json` только адреса. Символизировать самому:
  `llvm-symbolizer --obj=<бинарник> --inlines --demangle --output-style=LLVM` (адреса = RVA, для этого PIE работает как есть).
  Бинарник для символизации должен быть **тот же**, под которым снят профиль.
- Скрипты анализа лежат в scratchpad сессии (могут исчезнуть): `.../scratchpad/an2.py` (self/incl по потокам),
  `drv.py`/`drv2.py` (кто вызывает драйвер/`create_buffer`). Логика: по `stackTable`/`frameTable` брать `address`,
  библиотеку — через `funcTable.resource → resourceTable.lib → libs[].name`, символизировать адреса `ezzmc-client`.
  Потоки: главный поток называется `ezzmc-client` (несколько потоков с этим именем — брать с max числом сэмплов), мешеры `mesh-N`.

## 4. Что показал профиль (обычный мир, полёт, главный поток)

Полный экран, release+символы:
- ~24% self в `libnvidia-glcore` (драйвер) + ~21% в `libc` (ожидание/syscalls). Из них явные: `present` ~6%, `begin_encoding`, `submit`.
- `TerrainArena::resort` ~16%: из них `SortState::sorted_order` ~7% (сортировка), **хеширование `SectionPos` SipHash ~6%+4.5%** (`HashMap::get`, `make_hash`).
- `prepare_draws` ~8% (+ `sort_by` по `dist` с пересчётом на каждое сравнение).
- `Mobs::bake` → `Model::bake` ~10% (запекание моделей каждый кадр; в этом мире мобов быть не должно — **проверить, что именно запекается**, возможно игрок/пустые модели).
- Частицы `ParticleDraw::prepare_split/push_vertex_raw` ~4.6%.
- Лишние syscalls/буферы каждый кадр: `queue.write_buffer` создаёт staging-буфер (`create_buffer`/`destroy_buffer`/`StagingBuffer::write` ≈ 4% главного потока). Вызовы: `render_view` (~3.9%), `ParticleDraw::prepare_split`, `TerrainArena::resort` (по записи на секцию), `write_src_cmds` (по 20 Б на слот/слой), `upload`, `TextRenderer::flush`, `atlasanim::upload`, `GuiPainter::flush`.
  **Идея**: объединять мелкие `write_buffer` (один staging на кадр / переиспользуемый ring), особенно resort и write_src_cmds.
- `debugscreen::rss_mib` ~1.9% (читал /proc каждый кадр при открытом F3) — **исправлено** кешем 1 с.
- `input::Mouse::maintain` ~1% (`set_cursor_position` каждый кадр при захвате) — **не трогал** (ванильное поведение захвата, нужен тест).

Потоки мешинга (`mesh_section` ~94% их времени): `should_render_face` 38% incl, `face_rects` 21%, `Padded::fill` 15%, `Neighborhood::block` 12%,
`Tints::color`/`blend_tint` ~8% (биом-смешивание на каждый блок, в т.ч. `water_tint`), `Kind::index`/`BitStorage::get`/`state_props` (палитра), `Vec<[f64;4]>::push` (аллокации).
Идеи: кеш тинта по колонке/биому, избавиться от `Vec<[f64;4]>` на лице (SmallVec/переиспользование), быстрый путь для воздуха/полных блоков, `Padded::fill` через проход по секциям, а не по блокам.

## 5. Что уже изменено в коде (НЕ закоммичено; `cargo check -p ezzmc-client` и `cargo test -p ezzmc-mesh` (30 ok) проходили до последней правки `debugscreen.rs`)

1. `Cargo.toml` — профиль `fast`: `debug="line-tables-only"`, `strip="none"`. `.cargo/config.toml` — alias `f`.
2. `crates/render/src/terrain.rs`: загрузка вершин (`upload`) и indirect-команд (`prepare_draws`) копирует блоками (`Vec::with_capacity` + `extend_from_slice(&to_bytes())`) вместо `flat_map(...to_bytes).collect()` (на загрузке мира `upload` ≈ 24% кадра, 19.5% — этот flat_map).
   Карты `sections`/`sort` теперь `rustc_hash::FxHashMap` (alias `use rustc_hash::FxHashMap as HashMap`, `HashMap::default()`).
3. `crates/mesh/src/queue.rs`: `RebuildQueue::take` — приоритет считается один раз, `select_nth_unstable_by` + сортировка только `n` лучших вместо полной `sort_by` (порядок результата тот же; тесты `queue::tests` проходят). `FxHashSet`.
4. `crates/mesh/src/sort.rs`: `sorted_order` сортирует `u64`-ключи `(!f32_bits<<32)|idx` (`sort_unstable`) — тот же порядок (дальние первыми, равные — по индексу). Тест `far_to_near_and_stable` проходит.
5. `crates/mesh/src/pool.rs` (`generation`), `crates/client/src/worldview.rs` (`resident`, `vox_resident`) — `FxHash*`. ВНИМАНИЕ: в `worldview.rs:358` остался `std::collections::HashSet::new()` с полным путём — не заменять.
6. Зависимость `rustc-hash = "1.1"` добавлена в `crates/{mesh,render,client}/Cargo.toml` (уже была в Cargo.lock транзитивно). По правилам проекта нужна строка в `STATUS.md → Решения` — **ещё не добавлена**.
7. `crates/client/src/debugscreen.rs`: `rss_mib` кешируется на 1 с (статический `Mutex<Option<(Instant,u64)>>`). **Эту правку после написания не компилировали.**
